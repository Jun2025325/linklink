- 卡片是漂浮在黑色宇宙中的 3D 动物方块。
- 玩家可以旋转、移动游戏主体，从不同角度观察立方体棋盘。

## 2. Vibe Coding 的 Prompt 结构

本轮反复验证有效的 Prompt 不是简单描述“帮我做得好看”，而是把主观感受转成可执行的工程规格：

```text
感受 + 目标行为 + 空间语义 + 视觉约束 + 技术边界 + 禁止事项 + 验证证据
```

### 2.1 推荐通用骨架

```text
请基于当前项目实现 / 优化 {功能}。

我的感受：
- 当前问题是 {主观体验，例如：像网页、没空间感、拖动闪烁、手势不准}
- 我期望的感受是 {目标体验，例如：像漂浮在空间里、手一捏就能拿住}

目标：
- {明确结果 1}
- {明确结果 2}
- {明确结果 3}

空间语义：
- 位置使用 Stage 空间，注意真机 / 模拟器 Z 轴差异
- 交互使用 {DirectPinch / GazePinch / RayBasedPinch / Poke}
- {对象} 的移动 / 旋转 / 点击必须分离

视觉约束：
- {颜色、厚度、圆角、字号、遮挡、风格}

工程约束：
- 只使用 SpatialUI / PicoTheme
- 不使用 Material3 / Scaffold
- 关键资源 `toGlobal()`，销毁时显式 close
- 不在每帧创建 Entity

禁止：
- {明确不要做的事}

验收：
- `./gradlew testDebugUnitTest assembleDebug`
- 模拟器或真机启动无 FATAL / ANR
- 输出关键日志：{log tag}
- 用户实际手势 / 肉眼确认 {体验目标}
```

### 2.2 本项目最重要的 Prompt 原则

1. **先定义状态机，再做视觉**
   - Initial、Playing、MenuOpen、Cleared、TimedOut 必须先分清。
   - 否则容易出现“开始后菜单还在”“点击菜单穿透”“通关提前出现”等问题。

2. **主观风格必须落到具体材质和尺寸**
   - “空间感”要转成：悬浮、厚度、投影、深度、可拖动、遮挡关系、360° 背景。
   - “网页感”要禁止：白底表单、下拉框、大背板、纯 2D 按钮。

3. **手势必须定义完整生命周期**
   - 短捏、长捏、拖动、双手、释放、替换、错误状态都要写清。
   - 不要只说“支持手势”。

4. **真机与模拟器必须分开验收**
   - 模拟器可验证渲染和基础流程。
   - 手感、音频、佩戴舒适度、360° 背景、面板拖动必须真机确认。

5. **每个交互要有日志**
   - 手势不生效时，日志比截图更有用。
   - 关键 log 是后续回归测试的证据。

## 3. 优化后的核心 Prompt

以下 Prompt 整合了本轮多轮迭代后的最终需求，可用于重建同类项目，也可拆分成阶段执行。

### 3.1 星连立方核心重建 Prompt

```text
请创建一个 PICO Spatial SDK Full-space 应用。

应用信息：
- 名称：星连立方
- 包名：com.linklink.myspatial
- 容器：DefaultStage，StageStyle.Full，immersion 100%
- UI：只使用 SpatialUI / PicoTheme，禁止 Material3 / Scaffold

产品目标：
做一个黑色宇宙中的 3D 连连看。玩家在 Full-space 里观察、旋转、移动一个
N×N×N 动物方块棋盘，找出可以连接的相同卡片并消除。

核心玩法：
1. 卡片是 3D cube，每张卡使用一个完整不透明纹理。
2. 纹理一次性烘焙背景色、动物 emoji、边框和选中态。
3. 六个面共享同一套纹理，旋转时视觉稳定。
4. 两张卡消除必须满足：
   - 动物相同
   - 底色相同
   - 存在最多 3 个弯的 3D 折线路径
5. 路径可沿 X / Y / Z 方向行走，可使用已消除空格和外围 shell。
6. 路径不能穿过仍存在的卡片。

难度：
- 提供 3×3×3、4×4×4、5×5×5、自定义边长
- 自定义边长不设上限
- 奇数棋盘保留 1 个空位，使剩余卡片能成对
- 空位放在内部 median cell，保持外部视觉完整
- 通关后提供“下一关”和“返回菜单”

模式：
1. 休闲模式
   - 不计时
   - 眼神 / 射线目标 + GazePinch 确认
   - 第一张选中高亮，第二张判定
2. 手感模式
   - 左右手各可粘住一张卡
   - 两卡接近时出现能量线和磁吸
   - 两卡接触时判定配对
   - 非法配对软弹开，卡片仍可替换
   - 短捏选卡；捏住约 320ms 后可旋转游戏本体
   - 双手都已持卡时不旋转棋盘，保证配对动作稳定
3. 限时挑战
   - 使用休闲点选操作
   - 时间公式：90s + 每对 16s，按 30s 取整，最低 3 分钟
   - 菜单展开时暂停倒计时
   - 时间失败后显示重试 / 返回菜单

空间背景：
- 使用黑色宇宙背景
- 全向覆盖 360°，转身不能露出系统环境
- 使用 14m 内向球体，不使用会漏缝的 cube shell
- Material culling 设为 NONE
- DepthTest / DepthWrite 开启
- 增加多个近透明 keep-alive anchor，避免转身后 Full Stage 被系统隐藏

空间 UI：
- 开始面板是深色宇宙玻璃面板，不是白底网页表单
- 难度 / 模式使用圆角卡片
- 规则压缩成一行
- 开始后面板收起，只保留右侧工具栈
- 工具栈包含：菜单、提示、洗牌、放弃
- 工具是独立深色胶囊，不使用大背板
- 面板和工具栈支持直接拖动
- AttachmentPanel 拖拽手势挂在 UI 节点上，
  `detectSpatialDragGesture(targetedToEntity = null)`
- 位置 clamp 在舒适视野内

反馈：
- 卡片选中 pop 音
- 按钮 hover / click 音
- 匹配成功 / 失败音
- 双卡接近能量线
- 双卡接触星尘
- 成功汇聚成星
- 失败软弹开
- 匹配路径显示真实 solver path
- 提示显示引导路径
- 洗牌飞行动画和拖尾
- combo 音高变化和连击卡片
- 通关星座、烟花、礼炮、TTS“恭喜成功”

工程要求：
- 游戏逻辑与渲染分离，solver 写成纯 Kotlin 并有单元测试
- Texture / Material / Mesh 使用 `toGlobal()`
- Scene destroy 时显式 close
- 粒子使用固定 pool，不在每帧创建 Entity
- 真机与模拟器 Z 轴方向差异必须显式处理
- 模拟器可使用 Direct 3D fallback 菜单，真机使用 SpatialUI AttachmentPanel

验收：
- `./gradlew testDebugUnitTest assembleDebug`
- 3D 路径求解、奇数棋盘、提示、洗牌、限时公式有单元测试
- 模拟器渲染无崩溃
- 真机启动 MainStage visible、无 FATAL / ANR
- 手势、音频、360° 背景、面板拖动必须由用户真机确认
```

## 4. 关键迭代 Prompt

这些 Prompt 是从实际开发中的有效指令提炼而来，保留关键技术细节，去除重复描述。

### Prompt A：项目结构与入口确认

适用：接手已有项目或继续开发前的第一句指令。

```text
请先阅读当前项目的 AGENTS.md、Gradle 配置、Manifest 和主要源码。
告诉我：
1. 这是一个什么类型的 PICO Spatial 项目
2. 主要代码文件有哪些
3. 应用入口在哪里
4. 当前容器是 Volumetric Window Container 还是 Full-space Stage
5. 当前 SDK 版本和关键依赖

暂时不要改代码。
```

**沉淀原因**：先确认项目结构，避免把 Full-space 项目误按 WindowContainer 或普通 Android Compose 项目处理。

### Prompt B：3D 连连看 MVP

适用：从空场景进入可玩核心逻辑。

```text
请实现 3D 连连看 MVP。

棋盘：
- 初始 {4×4×4}
- {16 / N³} 张卡片，成对分布
- 每张卡是 3D 方块，先平铺在一个空间平面验证逻辑

规则：
- 不计时
- 点击第一张卡高亮
- 点击第二张卡后判定
- 图形相同且存在合法路径则消除
- 全部消除后显示“恭喜通关”

路径：
- 支持 3D 空间 X / Y / Z 方向
- 最多 {2 / 3} 个弯
- 可走外围
- 不能穿过其他卡片

交互：
- 使用射线检测选中卡片
- 消除播放缩放消失动画

验收：
- 核心逻辑写成纯 Kotlin 类
- 路径算法有单元测试
- 模拟器中能完成一局
```

**实际迭代后的关键修正**：

- 3D 空间路径最终放宽为最多 3 弯，更适合体感观察。
- 奇数棋盘保留一个内部空位，避免孤立卡片。
- 大棋盘身份可重复，但必须成对出现。

### Prompt C：动物卡片纹理与旋转稳定性

适用：解决方块不清晰、旋转后贴纸丢失、底色不同步。

```text
请把纯色方块卡片升级为动物卡片。

视觉：
- 每张卡保留彩色背景
- 正面中央显示足够大的动物 emoji
- 使用 8 种动物：
  🐱猫、🐶狗、🐰兔子、🦊狐狸、🐻熊、🐼熊猫、🐸青蛙、🐵猴子
- 每种动物 2 张，共 16 张
- 选中时整卡放大 / 发光，包括 emoji

后续升级到 4×4×4 后：
- 使用 64 种“动物 + 底色”身份
- 大棋盘可重复身份，但必须完整成对

关键技术：
- 一张卡 = 一个 cube = 一个完整纹理
- 纹理一次性烘焙背景、emoji、边框、选中态
- 六个面共享同一纹理
- 不给六个面分别换贴纸
- 不在旋转时动态补贴图

资源：
- Texture / Material / Mesh 使用 `toGlobal()`
- destroy 时显式 close

验收：
- 左右旋转、上下旋转后卡片视觉稳定
- 选中态整卡同步
- 无材质泄漏或崩溃
```

### Prompt D：游戏主体移动与旋转

适用：定义棋盘拖动，避免移动、旋转、选卡互相干扰。

```text
请优化游戏主体的空间拖动行为。

交互定义：
- DirectPinch 拖动游戏主体：移动位置
- GazePinch / RayBasedPinch 拖动游戏主体：旋转 yaw / pitch
- 短点卡片仍然只做选卡

手感模式补充：
- 短捏卡片 = 选卡 / 粘到对应手
- 捏住约 320ms 不松手 = 允许旋转游戏本体
- 左右手都已持卡时禁止棋盘旋转，优先保证双卡相碰

禁止：
- 不要长按后在移动 / 旋转模式间跳变
- 不要让面板双手手势直接套到游戏主体
- 不要拖卡片时同时拖动整个棋盘

验收：
- 位置移动和视角旋转分离
- 短点不误触发移动 / 旋转
- 手感模式双卡相碰不被旋转干扰
```

### Prompt E：手感模式双卡相碰

适用：把“拍掌”改成更自然的双卡确认。

```text
当前手感模式的拍掌动作尴尬且追踪不稳定，请重新定义确认动作。

旧交互：
- 左右手拍掌消除

新交互：
- 左手点一张卡，卡片粘在左手附近
- 右手点一张卡，卡片粘在右手附近
- 双手向中间靠近，但手掌不需要接触
- 当两张卡本身接触时触发判定

替换：
- 同一只手点另一张卡时，替换当前卡
- 不需要先把错误卡放回原位

错误释放：
- 只有明确、持续的手部快速运动才释放该手卡片
- 不允许加速度单独触发释放

反馈：
- 接近：金色能量线、轻微放大、软磁吸
- 接触：星尘冲击
- 合法：汇聚成星并消失
- 非法：软弹开，卡片留在手上

左右手识别：
- GazePinch 可能不带手别
- 不比较 inputDevicePose.rawPosition 和 HandTracking 全局坐标
- 优先读取左右 pinch strength / aim strength
- 只有一只手可见时使用该手
- 一只手已持卡且信号模糊时，第二张分给空手

日志：
- feelHandSignal
- feelCardTap
- feelCardsTouch
- feelFlickRelease
```

**实际踩坑**：

- `inputDevicePose.rawPosition` 与手部追踪坐标不在同一空间，直接算距离会导致左右手随机分配错误。
- 加速度阈值单独作为释放条件，会在手几乎静止时误释放。

视觉：

- 每个选项有主标题、短副标题、emoji 图标

### Prompt G：面板拖动稳定性

适用：开始面板、游戏内菜单、工具栈拖动，尤其处理闪烁和拖不动。

```text
请让 {开始面板 / 工具面板} 支持直接拖动。

期望：
- 用户捏住面板任意区域直接拖
- 不需要专门拖动把手
- 不显示“拖动”文字
- 短点按钮仍然执行点击

技术要求：
- AttachmentPanel 的手势挂在 UI 节点上
- 使用 `detectSpatialDragGesture`
- `targetedToEntity = null`
- 使用 SDK 返回的 `dragAmount`
- X / Y 跟随，Z 固定或强阻尼，避免前后闪烁
- 位置 clamp 在舒适视野内

禁止：
- 不要用外层 SpatialView 绑定的 panel anchor 作为 target
- 不要用 inputDevicePose.rawPosition 与 UI position3D 混算
- 不要每次拖动重建整个大面板

日志：
- setupPanelDragStartV2
- setupPanelDragMoveV2
- setupPanelDragEndV2
- toolRailDragStart
- toolRailDragEnd

验收：
- 面板稳定跟随
- 不前后闪
- 拖动后按钮仍可点击
```

**实际踩坑**：

- Runtime 对 2D 面板命中的 entity 和 AttachmentPanel anchor entity 可能不同，绑定 anchor 会导致手势完全不启动。
- 直接改 Entity Transform 而没有同步 Compose 状态，也可能导致面板视觉不更新。
- 手部深度抖动会放大成面板前后闪烁，最终方案限制 Z 轴。

### Prompt H：360° 黑色宇宙背景

适用：Full-space 沉浸式背景。

```text
请把空间背景改成黑色宇宙，并保证 360° 全沉浸。

要求：
- 玩家转身任何方向都只能看到星空，不允许露出 PICO 系统房间
- 不因视角放大 / 缩小漏出系统背景
- 背景缓慢流动或旋转

技术方向：
- 使用全向 cosmos sphere
- 半径足够大，例如 14m
- Material culling = NONE
- DepthTest 开启
- DepthWrite 开启，避免 PICO 硬件上背景变成纯黑或消失
- 增加围绕玩家的近透明 keep-alive anchor

禁止：
- 不要用有接缝或裁切面的 cube shell 作为最终方案
- 不要为了修漏背景而把主体隐藏
- 不要关闭 DepthWrite，除非已经真机验证不会黑屏

验收：
- 左转、右转、背后均看到星空
- 游戏主体仍在星空空间内
- 无系统环境露出
- 真机佩戴后确认
```

**实际结果**：

- 14m 全向 sphere 是最终实现。
- `StageKeepAliveRing()` 使用多个近透明 anchor 保持 Full Stage 活跃。
- 用户曾确认 360° 星空效果达到预期；后续版本需在最终 APK 上回归确认。

### 7.3 不建议复用的做法

1. **不要只说“做得有空间感”**
   - 必须列出深度、遮挡、透视、拖动、360°、厚度等具体要素。

2. **不要让模型同时大改多个系统**
   - 背景、手势、UI、图标应分阶段迭代。

3. **不要把模拟器验证当成最终验收**
   - 空间手势、音频、佩戴舒适度必须真机确认。

4. **不要用 2D tap 验证 3D 手势**
   - ADB tap 不能证明 DirectPinch、GazePinch、手部追踪或面板拖动有效。

5. **不要直接比较不同坐标空间**
   - UI position、inputDevicePose、hand tracking anchor 不是天然同一空间。

6. **不要只保存 APK**
   - 可回滚版本必须包含源码、配置、校验和版本说明。

## 8. 一句话总结

这轮 Vibe Coding 最有效的经验是：

> 把“我觉得没空间感 / 不好看 / 手感不对”翻译成明确的空间行为、状态机、手势生命周期、视觉材质、禁止事项和真机验收标准；每轮只解决一个主要原因，并用日志和截图留下证据。
